# Правила работы в репозитории OmniSecretary

Документ для AI-агентов и людей. Читать перед любой правкой.

## Что это за проект

Self-hosted AI-секретарь на Raspberry Pi 4 (4 ГБ). Ядро — Open WebUI в Docker.
Веб, Telegram, API и голос — окна к одному бэкенду и одной базе.

## Железные правила

1. **Никаких секретов в репозитории.** Только `.env.example` с плейсхолдерами.
   Реальные токены — в `.env` (в `.gitignore`) или в env контейнера.
   Никогда не печатать содержимое `.env` в чат, логи, README, коммиты.
2. **Опасные команды — только с явным подтверждением пользователя.**
   `sudo`, `apt`, `docker` (кроме read-only), `systemctl`, правка `/etc/fstab`,
   форматирование дисков, `rm -rf` вне репозитория. Вместо выполнения —
   писать идемпотентный скрипт и просить разрешение на запуск.
3. **Версии образов фиксированы.** Никаких `latest`. Обновление — отдельный
   осознанный коммит с правкой тега в `docker-compose.yml`.
4. **ARM64 обязателен.** Перед добавлением образа проверить наличие
   `linux/arm64` в манифесте.
5. **Локальные LLM на Pi не запускать.** Только облачные OpenAI-совместимые API.
6. **Память — дефицитный ресурс.** Новый сервис в compose обязан иметь
   `mem_limit` и обоснование в `docs/decisions.md`.
7. **Публичная регистрация и открытый Telegram-бот запрещены.**
8. **Инструменты с shell/GitHub — с ограничениями.** Любая деструктивная
   операция требует подтверждения пользователя в интерфейсе.

## Язык и стиль

- Документация, комментарии в коде, сообщения коммитов — **на русском**.
- Коммиты — Conventional Commits: `feat:`, `fix:`, `docs:`, `chore:`, `refactor:`.
- Пример: `feat: добавлен Qdrant и healthcheck в compose`.
- Комментарии объясняют «почему», а не «что».

## Git

- Ветка `main` — рабочая.
- Баг: ветка `fix/краткое-описание` → фикс → merge в `main` → удалить ветку.
- Крупная фича: `feature/краткое-описание`.
- Перед коммитом: `git status` и `git diff`.
- После каждого этапа: обновить README/docs, прогнать `make smoke`, коммит.

## Этапы

Работаем строго по [docs/plan.md](docs/plan.md). Не начинать следующий этап,
пока текущий не прошёл smoke-тест и не закоммичен. Каждый этап заканчивается:
- обновлением документации;
- healthcheck/smoke-проверкой;
- коммитом с понятным сообщением.

## Структура

```
docker-compose.yml     стек (фиксированные теги, лимиты памяти)
nginx/                 reverse proxy, WebSocket, TLS-заготовка
scripts/               bootstrap, smoke, backup, update
docs/                  архитектура, решения, безопасность, план
presets/               пресеты-«лица» (этап 2)
mcp/                   конфиги MCP-серверов (этап 4)
```

## Проверки перед сдачей работы

```bash
bash -n scripts/*.sh            # синтаксис скриптов
docker compose config -q        # валидность compose
./scripts/smoke-test.sh         # здоровье стека
```

Не утверждать «готово», пока проверки не выполнены и не показан их вывод.

## Что нельзя ломать

- Единая база: чаты из веба и Telegram должны быть видны в одном месте.
- Приватный режим: не сохранять и не обращаться к истории/памяти.
- Идемпотентность `bootstrap-pi.sh` и `backup.sh`.
- Возможность переноса `${DATA_ROOT}` на внешний диск без потери данных.

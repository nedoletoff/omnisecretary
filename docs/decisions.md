# Принятые решения и допущения

Формат: ADR (контекст → решение → альтернативы → последствия).
Дата фиксируется по факту принятия.

---

## ADR-001. Open WebUI как единое ядро

**Контекст:** нужны веб, Telegram, API, память, инструменты, многопользовательность.

**Решение:** Open WebUI — единственный бэкенд и единственная база. Telegram-бот
(этап 3) пишет в те же чаты через API, а не в отдельную БД.

**Альтернативы:** собственная обвязка на FastAPI + отдельные боты — больше кода,
дублирование чатов; LibreChat — тяжелее и слабее по MCP/пресетам.

**Последствия:** зависимость от API Open WebUI; версия фиксируется.

---

## ADR-002. PostgreSQL вместо SQLite

**Контекст:** многопользовательский режим, одновременные записи из веба и бота.

**Решение:** `pgvector/pgvector:0.8.7-pg16` — PostgreSQL 16 со встроенным pgvector.

**Почему не `postgres:16-alpine`:** pgvector даёт резервный векторный бэкенд
без смены образа, если Qdrant окажется неудобен.

**Последствия:** +150–200 МБ ОЗУ; бэкап через `pg_dump -Fc`.

---

## ADR-003. Qdrant как основная векторная память

**Контекст:** на 4 ГБ ОЗУ нужен предсказуемый и лёгкий векторный движок.

**Решение:** Qdrant `v1.19.2`, `QDRANT_ON_DISK=true`, `ON_DISK_PAYLOAD=true`.
Версия выровнена с `qdrant-client 1.18.0`, который поставляется внутри
Open WebUI v0.13.3: разница минорных версий ≤ 1, клиент не предупреждает
о несовместимости.

**Альтернативы:** pgvector — меньше сервисов, но хуже фильтрация и масштабирование
памяти; Chroma — тяжелее и менее стабилен на ARM.

**Последствия:** +512 МБ лимита; снапшоты через HTTP API на `127.0.0.1:6333`.

---

## ADR-004. Контейнерный nginx вместо нативного

**Контекст:** на хосте уже установлен nginx, занят порт 80.

**Решение:** nginx в compose (`1.30.6-alpine`); bootstrap предлагает
`systemctl disable --now nginx` с подтверждением.

**Альтернативы:** нативный nginx как reverse proxy — проще, но конфиг вне
репозитория, расходится с целевой архитектурой и усложняет перенос.

**Последствия:** нативный nginx отключается (конфиги сохраняются);
`cloudflared` на хосте проксирует на `127.0.0.1:80`.

---

## ADR-005. Redis для веб-сокетов

**Контекст:** несколько вкладок + Telegram + API одновременно.

**Решение:** `redis:8.8.4-alpine`, `maxmemory 64mb`, `allkeys-lru`,
`WEBSOCKET_MANAGER=redis`.

**Последствия:** сессии переживают рестарт open-webui; Redis не хранит
пользовательские данные (только кэш/сокеты), поэтому в бэкап не входит.

---

## ADR-006. Облачные LLM, без локальных LLM

**Контекст:** 4 ГБ ОЗУ; локальная LLM неприемлема по скорости и памяти.

**Решение:** `ENABLE_OLLAMA_API=false`; LLM — облачная, OpenAI-совместимая.

**Последствия:** нужен интернет и API-ключ; расходы контролируются выбором
модели. Эмбеддинги вынесены в ADR-031 (локальные).

---

## ADR-007. Telegram-бот — собственный сервис, не плагин

**Контекст:** у Open WebUI нет официального Telegram-бота; готовые форки
не гарантируют запись в те же чаты.

**Решение (этап 3):** сервис `bot/` на `python-telegram-bot` + `httpx`,
long polling (без публичного webhook), авторизация по allowlist,
запись через `/api/chat/completions` с `chat_id`.

**Последствия:** полный контроль над allowlist и логами; нужно поддерживать
совместимость с API Open WebUI.

---

## ADR-008. Календарь — Radicale, задачи — Vikunja

> **Частично заменено ADR-016:** Radicale не ставим — встроенный календарь
> Open WebUI v0.13.3 не поддерживает CalDAV. Задачи Vikunja остаются.

**Контекст:** нужны календарь и список задач «сейчас», без внешних сервисов.

**Решение:** Radicale (CalDAV, лёгкий) + Vikunja (задачи, веб-UI).
Встроенный календарь Open WebUI подключается к Radicale по CalDAV.
MCP-сервер Vikunja — этап 4.

**Альтернативы:** Baikal — тяжелее (PHP+MySQL); Nextcloud — избыточен для Pi.

**Последствия:** +2 контейнера (этап 2); Vikunja использует отдельную БД.

## ADR-009. MCP — внешние серверы, а не in-process плагины

**Контекст:** инструменты должны быть изолированы и обновляемы отдельно.

**Решение:** каждый MCP-сервер — отдельный контейнер/сервис с минимальными
правами; доступ через MCP-прокси Open WebUI.

**Последствия:** больше контейнеров; зато падение инструмента не роняет ядро,
а права ограничиваются на уровне контейнера.

---

## ADR-010. Секреты только через `.env`

**Решение:** `.env` генерируется bootstrap (`openssl rand`), права 600,
в git только `.env.example`. Пароль Postgres — hex (URL-безопасный).

**Последствия:** бэкап `.env` не делается автоматически; при потере —
пересоздание секретов и перелогин (данные не теряются).

---

## ADR-011. Диск данных: SD сейчас, внешний HDD позже

**Контекст:** внешний диск ещё не подключён, есть SD 128 ГБ.

**Решение:** `${DATA_ROOT}` — переменная. Сейчас `/srv/omnisecretary`,
после подключения диска — `/mnt/data/omnisecretary`. Docker data-root
переключается в `/etc/docker/daemon.json`. Процедура — в
`docs/architecture.md` («Перенос на внешний диск»).

**Последствия:** образы после переноса скачиваются заново; данные
переносятся `rsync -aHAX`.

---

## ADR-012. Внешний доступ: LAN по умолчанию, Cloudflare Tunnel для интернета

**Контекст:** нет арендованного сервера и, возможно, нет белого IP.

**Решение:** по умолчанию только LAN (`http://192.168.0.102`).
Для внешнего доступа — Cloudflare Tunnel (уже установлен) либо
Let's Encrypt при наличии домена. Порты наружу не пробрасываются.

**Последствия:** публичный доступ возможен без открытых портов; TLS —
на стороне Cloudflare.

## ADR-013. Лимиты памяти в compose

**Решение:** `mem_limit` у каждого сервиса (см. `docs/architecture.md`).
Потолки заданы по сервисам (Open WebUI 1,5 ГБ, Postgres 384 МБ, Qdrant
512 МБ, остальные 32–640 МБ); фактическое потребление — около 1,7 ГБ
при 3,7 ГБ ОЗУ и 2 ГБ swap.

**Последствия:** при нехватке памяти контейнер будет убит OOM, а не утянет
весь хост; диагностика — `docker stats`, `dmesg | grep -i oom`.

**Важно:** на Raspberry Pi лимиты работают только при включённом
memory-cgroup. Если `/sys/fs/cgroup/cgroup.controllers` не содержит `memory`,
Docker пишет «memory limit capabilities ... discarded» и лимиты игнорируются.
Исправление: `scripts/enable-memory-cgroup.sh` (добавляет
`cgroup_enable=memory cgroup_memory=1` в `/boot/firmware/cmdline.txt`) + ребут.
**Выполнено 13.11.2026:** после перезагрузки `memory` есть в controllers,
контейнеры пересозданы, `docker stats` показывает лимиты (`701 MiB / 1.5 GiB`).

## ADR-014. Obsidian-вольт: приватный git, доступ только владельцу

**Контекст:** вольт пользователя лежит в приватном git-репозитории; ИИ должен
писать в отдельные папки, но не засорять контекст и не светить токен.

**Решение:**
- Клон в `${DATA_ROOT}/vault`, отдельный сервис `vault-sync` для подключения
  через веб-форму и git pull/commit/push.
- `obsidian-mcp` с FTS5-индексом: сначала поиск, потом чтение найденного;
  в контекст попадают только сниппеты и запрошенные страницы.
- Каждая запись — коммит `vault: <действие> <путь>`.
- Инструменты вольта включены только в пресетах владельца; другие
  пользователи их не видят.
- Токен PAT — только в защищённом хранилище сервиса, не в git и не в чате.

**Альтернативы:** загрузка вольта в Knowledge Open WebUI — дорого по токенам
и памяти, нет контроля записи; монтирование вольта в контейнер open-webui —
нет per-user изоляции.

**Последствия:** два дополнительных лёгких контейнера; нужен PAT с
`Contents: read/write` на один репозиторий. Подробно — `docs/obsidian.md`.

## ADR-015. Vikunja на отдельном порту, отдельная БД в общем PostgreSQL

**Контекст:** Vikunja нужна сейчас; второй сервер БД на 4 ГБ — расточительно.

**Решение:**
- Vikunja `2.8.0` (arm64) в compose; образ distroless (нет shell), поэтому
  healthcheck делает smoke-тест через HTTP, а не Docker.
- Отдельная база `vikunja` в существующем PostgreSQL, создаётся одноразовым
  сервисом `db-init` (`docker/db-init.sh`, идемпотентно).
- nginx слушает `:8081` и проксирует в Vikunja: сервис не умеет жить
  в подкаталоге `/tasks/`.
- CalDAV Vikunja включён (`VIKUNJA_SERVICE_ENABLECALDAV=true`).

**Альтернативы:** отдельный PostgreSQL-контейнер (+~150 МБ ОЗУ) — отклонено;
проксирование по пути `/tasks/` — не работает без правки фронтенда Vikunja.

**Последствия:** порт 8081 виден в LAN; наружу не пробрасывать.
Instance-admin в Vikunja 2.x — платная функция, для одного пользователя
не нужна: пользователь создаётся CLI, проекты и задачи доступны обычному
аккаунту.

## ADR-016. Календарь — встроенный Open WebUI, Radicale отложен

**Контекст:** ТЗ требует CalDAV (Radicale/Baikal) и встроенный календарь.

**Проверено в коде Open WebUI v0.13.3:** есть роутер `/api/v1/calendars`
(календари и события в PostgreSQL, гранты доступа), но **нет** CalDAV/ICS-
синхронизации. Подключить встроенный календарь к Radicale нельзя.

**Решение:**
- События — во встроенном календаре Open WebUI (одна база, один бэкап).
- Задачи — Vikunja, она же отдаёт их по CalDAV в календарь телефона.
- Radicale/Baikal и двусторонняя синхронизация событий — этап 4, вместе
  с MCP-инструментами календаря; тогда же решим: CalDAV-мост или
  собственный MCP-сервер поверх API календаря Open WebUI.

**Последствия:** события с телефона пока не попадают в Open WebUI;
задачи — попадают (CalDAV Vikunja). Экономия ~40 МБ ОЗУ и одного контейнера.

## ADR-017. Пресеты — модели Open WebUI, импорт через API

**Контекст:** нужны «лица» (Secretary, Omni, Archivist, Coder, Private)
с разными промптами, моделью и доступом к инструментам.

**Решение:** пресеты хранятся как markdown-файлы с front matter
(`presets/*.md`) — версионируются в git, ревьюятся как код. Импорт —
`POST /api/v1/models/import` (скрипт `scripts/import_presets.py`),
идемпотентно по `id`. Базовая модель задаётся флагом `--base-model`,
поэтому пресеты не привязаны к конкретному провайдеру.

**Альтернативы:** ручное создание в UI (не версионируется, расходится
между установками); плагины/функции (сложнее, не нужно для промптов).

**Последствия:** после смены LLM-провайдера пресеты переимпортируются
одной командой. Доступ к пресетам разграничивается штатными грантами
моделей (этап 3, вместе с многопользовательским режимом).

## ADR-018. memory-cgroup на Raspberry Pi

**Контекст:** Docker на Pi пишет «memory limit capabilities ... discarded»,
`mem_limit` игнорируется, если ядро не включило контроллер памяти.

**Решение:** `scripts/enable-memory-cgroup.sh` добавляет
`cgroup_enable=memory cgroup_memory=1` в `/boot/firmware/cmdline.txt`
(с резервной копией) и требует перезагрузку. Идемпотентно.

**Последствия:** без перезагрузки лимиты не работают — риск OOM на 4 ГБ.
Проверка после ребута: `/sys/fs/cgroup/cgroup.controllers` содержит `memory`,
`docker inspect -f '{{.HostConfig.Memory}}' <контейнер>` больше нуля.
**Статус: включено 13.11.2026**, все контейнеры пересозданы с лимитами.

## ADR-019. Бесплатная тестовая LLM — Pollinations

**Контекст:** нужен работающий чат до появления ключа платного провайдера.

**Решение:** Pollinations (`https://text.pollinations.ai/openai`) —
OpenAI-совместимый endpoint без ключа, модель `openai-fast` (gpt-oss-20b).
Ключ-заглушка `pollinations` нужна только потому, что Open WebUI требует
непустой ключ. Провайдер задаётся через `/openai/config/update`, а не
правкой БД.

**Ограничения:** публичный бесплатный сервис, rate limit, данные уходят
третьей стороне. Только для тестов и демо, не для личных данных.
Для продакшна — OpenRouter/DeepSeek/Groq и свой ключ.

**Последствия:** `make init-webui` настраивает провайдера автоматически;
смена провайдера — правка `.env` + `make restart && make init-webui`.

## ADR-020. Тема Gruvbox через custom.css

**Контекст:** нужен единый Gruvbox-вид без форка фронтенда Open WebUI.

**Решение:** Open WebUI подключает `/static/custom.css` до основного
бандла и раздаёт его из `/app/build/static`. Монтируем `theme/gruvbox.css`
ровно в этот путь (в `backend/open_webui/static` монтировать нельзя —
backend копирует статику и падает с «are the same file»).
Переопределяем CSS-переменные Tailwind v4 (`--color-*`) с `!important`,
поэтому тема живёт в обоих режимах и не ломается при обновлении UI.

**Последствия:** тема — обычный файл в git, применяется рестартом.
При мажорном обновлении Open WebUI проверить, что имена переменных не
изменились.

## ADR-021. Telegram-бот: stdlib, отдельные аккаунты, long polling

**Контекст:** нужен бот с allowlist, теми же чатами, что в вебе, и
изоляцией пользователей; на Pi каждый мегабайт и каждая зависимость на счету.

**Решение:**
- бот написан на стандартной библиотеке (urllib + sqlite3), образ
  `python:3.12-slim` без pip-зависимостей — ~35 МБ в памяти;
- long polling вместо webhook: не нужен публичный адрес и TLS для Telegram;
- у каждого Telegram ID свой аккаунт Open WebUI; владелец маппится на свой,
  поэтому его чаты общие с вебом;
- сообщения пишутся через `/api/chat/completions` с `chat_id` и
  `user_message.id` — сервер сам дописывает пару в историю чата;
- приватный режим — запрос без `chat_id` (сервер не создаёт чат);
- модели открываются всем на `read` грантом: в v0.13 модель без грантов
  приватна, и обычный пользователь не увидел бы пресеты.

**Последствия:** бот не поддерживает файлы и голос (этап 5). При смене
формата `/api/chat/completions` в новой версии Open WebUI — проверить
`ask_saved`. Пароли автосозданных аккаунтов лежат в `bot.db` (600).

## ADR-022. MCP-инструменты — отдельные контейнеры, общий образ

**Контекст:** инструменты можно реализовать плагинами внутри Open WebUI или
внешними MCP-серверами.

**Решение:** все инструменты — внешние контейнеры (`mcp-vault`, `mcp-files`,
`mcp-github`, `mcp-vikunja`, `mcp-sandbox`) с streamable HTTP `/mcp`.
Общий образ `mcp/Dockerfile` (python:3.12-slim + mcp + git + curl).

**Почему:** падение или утечка инструмента не роняет ядро; у каждого свой
`mem_limit` (64–192 МБ); можно перезапускать по отдельности; код на Python
проще аудировать, чем JS-плагины внутри контейнера Open WebUI.

**Последствия:** пять контейнеров вместо одного — +544 МБ лимитов (фактически
~120 МБ в простое). Инструменты требуют сети `backend`; наружу не выходят.

## ADR-023. Доступ к инструментам: `access_grants` пустой = только админ

**Контекст:** вольт и GitHub должны быть доступны только владельцу, но
пресеты (модели) в Open WebUI по умолчанию приватны и требуют грантов.

**Решение:** tool servers регистрируются без `access_grants`. Open WebUI
трактует такой сервер как доступный только администратору. Пресетам
инструменты выдаются через `meta.toolIds`, а сами пресеты доступны всем
пользователям на чтение (иначе их не увидят в списке моделей).

**Почему:** единственный способ в v0.13.3 отделить «владельца» от «обычного
пользователя» без отдельной авторизации MCP.

**Последствия:** обычный пользователь видит пресеты, но при вызове
инструмента получает отказ доступа. Если Open WebUI изменит семантику
пустых `access_grants` — проверить после обновления (smoke не ловит это,
нужен ручной тест вторым аккаунтом).

## ADR-024. Вольт: FTS5-индекс, запись только в `AI/`, git на операцию

**Контекст:** вольт может быть большим; грузить его в контекст нельзя.
Нужны поиск, чтение по требованию и безопасная запись.

**Решение:**
- SQLite FTS5 в `${DATA_ROOT}/vault-index/vault.db`, инкрементальная
  переиндексация по mtime/размеру (только `*.md`);
- `vault_search` → путь + сниппет 14 слов; `vault_read` → не больше 4000
  символов за вызов;
- запись разрешена только в `AI/` (`VAULT_WRITE_PREFIX`), проверка на
  сервере, не в промпте;
- каждая операция записи — отдельный коммит; push в фоне через 2 с
  (серия записей уходит одним push).

**Почему:** экономия токенов и контекста — прямое требование; коммит на
операцию даёт откат и историю, а debounce не спамит origin.

**Последствия:** поиск по смыслу (эмбеддинги) не делается — только точный
FTS5. Семантический поиск по вольту — возможное расширение через Qdrant.

## ADR-025. Подключение вольта через веб-форму, токен вне git

**Контекст:** пользователь подключает приватный репозиторий сам, через
интерфейс, и не хочет править compose на Pi.

**Решение:** сервис `vault-manager` (FastAPI, 96 МБ) на `/vault/` за nginx,
HTTP Basic Auth (`VAULT_ADMIN_USER` / `VAULT_ADMIN_PASSWORD`). Форма:
URL, ветка, PAT. Клон в `${DATA_ROOT}/vault`; токен — в
`${DATA_ROOT}/secrets/vault-git-token` (600). Git получает токен через
`http.extraheader` на время команды, поэтому в `.git/config` его нет.

**Почему:** не нужен SSH-ключ на Pi и ручные правки; токен можно отозвать
в GitHub, не трогая сервер.

**Последствия:** Basic Auth по HTTP в LAN — приемлемо; при выходе за LAN
обязателен TLS (Cloudflare Tunnel или Let's Encrypt). Конфликты
`pull --rebase --autostash` разрешаются вручную, автоматического
`AI/Conflicts/` нет.

## ADR-026. Песочница вместо SSH/Computer Use

**Контекст:** ТЗ требует «действия на Pi» с подтверждением. Прямой SSH-MCP
к хосту означает доступ к `sudo`, `systemctl`, файлам ОС — высокий риск.

**Решение:** `mcp-sandbox` — контейнер без docker.sock, host-сети и
`privileged`, только `${DATA_ROOT}/sandbox`. Allowlist программ
(`python3`, `node`, `git`, `ls`, `grep`, …), запрет `sudo/apt/systemctl/
rm/dd/mount`, запрет метасимволов оболочки, таймаут 60 с, лимит вывода.

**Почему:** прототипы и код можно запускать безопасно; опасные операции
остаются за владельцем — это соответствует правилу «опасные команды только
с подтверждением» и убирает целый класс атак.

**Последствия:** ассистент не может сам перезапустить сервис или обновить
пакеты. Полноценный SSH/Computer Use — отдельный этап с выделенным ключом,
allowlist хостов и подтверждением в UI.

## ADR-027. STT: sherpa-onnx с моделью Vosk вместо vosk-python

**Контекст:** ТЗ требует Vosk (`vosk-model-small-streaming-ru`). На практике
`alphacephei.com` — единственный источник Kaldi-моделей — недоступен из сети
Pi: DNS отдаёт только IPv6 (`2a01:4f8:...`), маршрута нет; запросы по
IPv4-адресу тоже блокируются. Streaming-модель весит 597 МБ.

**Решение:** движок sherpa-onnx 2.0.1 (onnxruntime), модель
`alphacep/vosk-model-small-ru` с HuggingFace — это та же модель Vosk
(Zipformer2, обучена k2-fsa/icefall), но в ONNX-формате. int8-энкодер 25 МБ.

**Почему:** зависимость легче (нет Kaldi), на ARM быстрее, качество то же
(WER 9.8 на Common Voice ru). Модель скачивается при сборке с HF, который
доступен.

**Последствия:** распознавание offline (запись целиком), не потоковое:
7 с речи ≈ 10 с на Pi 4. Для голосового ввода в чат приемлемо. Если нужен
streaming — положить Kaldi-модель в образ вручную и вернуть `vosk`.

## ADR-028. TTS: Silero основной, Piper альтернатива

**Контекст:** Silero даёт естественный русский голос с ударениями, но тянет
torch (~350–500 МБ ОЗУ). Piper лёгкий (~60–90 МБ), но голос проще.

**Решение:** два образа из одного `app.py`:
- `voice/tts/Dockerfile` — Silero v4_ru (torch CPU, 640 МБ лимита), профиль
  `voice`;
- `voice/tts/Dockerfile.piper` — Piper `ru_RU-irina-medium` (192 МБ), профиль
  `voice-piper`.

Переключение — переменной `AUDIO_TTS_OPENAI_API_BASE_URL` (`http://tts:8000/v1`
или `http://tts-piper:8000/v1`).

**Почему:** ТЗ требует Silero основным, Piper — альтернативой; на 4 ГБ ОЗУ
нужен дешёвый путь отступления.

**Последствия:** одновременно два TTS не запускать. При включённом Silero
сумма лимитов стека превышает 4 ГБ — лимиты не резервация, но при нехватке
памяти отключайте TTS или переходите на Piper.

## ADR-029. Погода — api.met.no

**Контекст:** нужен бесплатный прогноз без ключа. `api.open-meteo.com`
из сети Pi не отвечает (таймаут маршрута), `wttr.in` отдаёт данные, но
обрывает соединение на 12 с.

**Решение:** MET Norway `locationforecast/2.0/compact` — 0,2 с, без ключа,
обязателен осмысленный `User-Agent`.

**Последствия:** погода на 12 часов, коды явлений переводятся в русский
вручную (`SYMBOLS`). Условия использования met.no требуют кэширования и
указания источника — при публичном использовании добавить атрибуцию.

## ADR-030. Брифинг — отдельный контейнер, а не плагин Open WebUI

**Контекст:** расписание должно работать без открытого браузера; плагин
внутри Open WebUI делит с ядром память и падает вместе с ним.

**Решение:** `proactive` — FastAPI + поток-планировщик, только stdlib для
HTTP, 96 МБ, профиль `proactive`. Читает API ядра, Vikunja и вольт.

**Почему:** независимый жизненный цикл, простой образ, нет зависимостей,
легко добавить напоминания и алерты.

**Последствия:** второй планировщик рядом с automations Open WebUI; секреты
бота и ключ API дублируются в env контейнера. Пропущенный из-за выключения
брифинг не догоняется (этап 7).

## Допущения

1. Пользователь — единственный администратор, создаёт аккаунты вручную.
2. Облачный провайдер поддерживает OpenAI-совместимые `/chat/completions`
   и `/embeddings`.
3. Часовой пояс хоста корректен; `TZ` берётся из `/etc/timezone`.
4. Внешний диск появится позже; до этого данные на SD и есть бэкапы.
5. Домен для HTTPS появится не сразу; LAN-режим достаточен для этапа 1.
6. `cloudflared` будет настроен пользователем отдельно (токен туннеля — секрет).

## ADR-019. Системный промпт — в `params.system`, персонаж и на базовой модели

**Контекст.** Пресеты хранили промпт в `meta.system`. В Open WebUI v0.13.3
фронтенд читает системный промпт модели из `params.system`; `meta.system`
сохраняется, но в запрос к LLM не попадает. Из-за этого все пресеты
работали без персонажа, а ассистент считал себя обычным чатом.

**Решение.**
- `scripts/import_presets.py` кладёт текст пресета в `params.system`.
- Импорт дополнительно применяет промпт `omnisecretary.md` к базовой модели
  (`/api/v1/models/model/update?id=<base>`), чтобы персонаж был и при выборе
  базовой модели, а не только пресета.
- Основной пресет — `omnisecretary`: знает, что живёт в OmniSecretary,
  перечисляет возможности и помогает с настройкой.

**Последствия.** Промпт уходит в каждый запрос (~550 токенов), поэтому он
держится компактным: без примеров и длинных инструкций. Проверка:
`GET /api/v1/models/model?id=<id>` → `params.system` непустой.

## ADR-031. Локальные эмбеддинги вместо облачных

**Контекст:** облачных ключей для эмбеддингов нет; Pollinations эмбеддинги
не поддерживает (404), а память и знания без них не работают. Бесплатный
тариф LLM не покрывает эмбеддинги.

**Решение:** `RAG_EMBEDDING_ENGINE=` (пусто) + `RAG_EMBEDDING_MODEL=all-MiniLM-L6-v2`.
Модель (~90 МБ) скачивается один раз в том Open WebUI и считается на CPU.
Потолок Open WebUI поднят до 2 ГБ (`memswap_limit` 2,5 ГБ).

**Проверено:** `POST /api/v1/retrieval/process/text` → 200, текст
проиндексирован; потребление Open WebUI ~0,9–1,3 ГБ.

**Последствия:** память и загрузка документов работают без внешних ключей;
+300–400 МБ ОЗУ при активном использовании. Семантический поиск по вольту
по-прежнему FTS5 (ADR-024), эмбеддинги вольта — возможное расширение.

## ADR-034. Шифрование пользовательских токенов в портале

**Контекст:** аудит показал, что GitHub-токен пользователя лежит в
`portal.db` открытым текстом. Дамп базы уходит в бэкап.

**Решение:** AES-256-GCM (`cryptography`), ключ в `/data/token.key`
(права 600). Формат `enc:v1:<nonce>:<ciphertext>`. При старте портал
шифрует записи, сохранённые до миграции.

**Последствия:** без файла ключа токены не восстановить — ключ нужно
включать в зашифрованный бэкап отдельно от базы. Потеря ключа = повторный
ввод токена пользователем, данные не страдают.

## ADR-035. Запись в GitHub выключена по умолчанию

**Контекст:** MCP-инструмент мог создать коммит или issue без отдельного
подтверждения. Prompt injection из письма/веб-страницы мог этим воспользоваться.

**Решение:** `GITHUB_WRITE_ENABLED=false` по умолчанию. Чтение (репозитории,
файлы, issues, поиск кода) работает всегда. Запись включается переменной
в `.env` и перезапуском.

**Последствия:** для правок через ассистента владелец явно включает запись.
Это осознанный компромисс между удобством и риском.

## ADR-036. Отдельная сеть для песочницы

**Контекст:** `mcp-sandbox` стоял в сети `backend` рядом с postgres, Qdrant,
Redis и Vikunja, а MCP-серверы с секретами — в `mcp`.

**Решение:** сеть `sandbox` только для `mcp-sandbox` и Open WebUI. Интернет
доступен (pip/npm), внутренние имена сервисов не резолвятся.

**Проверено:** из песочницы `postgres`, `qdrant`, `redis`, `vikunja`,
`mcp-github` → `gaierror`; `1.1.1.1:443` → OK.

**Последствия:** код в песочнице не может обратиться к базе или украсть
токены MCP. Если понадобится доступ к сервису — только явное добавление
в сеть, а не «на всякий случай».

## ADR-037. Панель состояния через файл, а не через API Docker

**Контекст:** нужна страница с температурой, памятью, диском и статусом
контейнеров. Монтировать `docker.sock` в портал нельзя.

**Решение:** cron раз в минуту запускает `scripts/device-status.py` от root
и пишет `${DATA_ROOT}/status/device.json` (644). Портал читает файл
(read-only) и показывает страницу `/portal/admin/status` только владельцу.

**Последствия:** ноль дополнительных контейнеров и мегабайт ОЗУ; история
не хранится (только последний снимок). Если cron не работает — страница
показывает «—», а не падает.

## ADR-019. LLM-шлюз с откатом на бесплатную модель

**Контекст:** OpenRouter — основной провайдер, но баланс может кончиться
(HTTP 402), ключ — отозваться, а бесплатная Pollinations отвечает не чаще
раза в 45 секунд. Прямое подключение OpenRouter в Open WebUI означало бы,
что при 402 чат просто перестаёт работать.

**Решение:** контейнер `llm-gateway` (96 МБ) реализует OpenAI-совместимый
`/v1/chat/completions`. Модель `omni-auto` идёт в OpenRouter, а при
401/402/403/404/429/5xx или сетевой ошибке повторяет запрос в Pollinations.
`omni-free` и алиасы `openai-fast`/`openai-large` всегда бесплатные,
`omni-openrouter` — только OpenRouter (для отладки ключа).

**Следствия:** Open WebUI не знает о сбоях провайдера; в ответе приходит
фактическая модель (`gpt-oss-20b` при откате). Потоковые ответы
проксируются как SSE. Стоимость — один лёгкий контейнер, без БД.

## ADR-020. Отдельный домен для календаря и заметок

**Контекст:** на телефоне нужен короткий адрес без полного интерфейса чата.
Домен `nedoletoff.mooo.com` уже указывает на белый IP.

**Решение:** nginx-vhost `30-mooo.conf` отдаёт только `/portal/quick`
(календарь и заметки), всё остальное редиректит на основной домен.
Аутентификация — портал, который хранит JWT пользователя в подписанной
cookie и обращается к API Open WebUI от его имени. Сертификат — отдельный
Let's Encrypt.

**Следствия:** нет второго списка пользователей и второй базы; изоляция
сохраняется. На домене нет чата, админки и вольта — уменьшена площадь атаки.

## ADR-021. Rootless Docker — поэтапно

**Контекст:** rootful-демон даёт контейнерам косвенный root на хосте.
Полный переезд требует переноса томов и простоя.

**Решение:** rootless-демон установлен и проверен рядом с rootful
(`uidmap`, linger, `ip_unprivileged_port_start=80`), но рабочий стек пока
на rootful. Переезд — отдельное окно по `docs/rootless.md` с бэкапом и
откатом.

**Следствия:** риск не переносится на рабочие дни; путь миграции проверен
на тестовом контейнере. CLI-контекст по умолчанию оставлен `default`,
чтобы существующие скрипты не сломались.
